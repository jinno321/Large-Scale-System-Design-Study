# 유튜브(YouTube) 설계

## 무엇을 설계하는가

유튜브 같은 동영상 스트리밍 서비스를 설계한다. 사용자가 동영상을 업로드하고, 다른 사용자가 그 동영상을 시청하는 것이 핵심이다.

겉보기엔 단순하지만, 규모가 커지면 어마어마하게 복잡해진다. 유튜브는 월간 활성 사용자 20억 명, 하루 시청 시간 50억 시간, 분당 500시간 분량의 동영상이 업로드되는 규모다. 이 설계의 본질은 **"거대한 동영상 파일을 어떻게 저장하고, 전 세계 사용자에게 어떻게 끊김 없이 전달하는가"** 이다.

## 문제 이해 및 설계 범위 확정

질문을 통해 요구사항을 확정한다.

- **중요한 기능은?** 동영상 업로드와 시청.
- **어떤 클라이언트를 지원하나?** 모바일 앱, 웹 브라우저, 스마트 TV.
- **DAU는?** 500만 명.
- **사용자의 하루 평균 시청 시간은?** 30분.
- **다국어 지원이 필요한가?** 그렇다.
- **지원하는 동영상 화질은?** 대부분의 화질과 해상도.
- **암호화가 필요한가?** 그렇다.
- **동영상 파일 크기 제한은?** 최대 1GB.
- **기존 클라우드 인프라를 활용해도 되나?** 그렇다.

정리하면 요구사항은 **빠른 업로드, 원활한 시청, 화질 선택 지원, 낮은 인프라 비용, 높은 가용성·확장성·안정성**이다.

## 개략적 규모 추정

```
DAU 500만
1인당 하루 5개 영상 시청 가정
10% 사용자가 하루 1개 영상 업로드
평균 영상 크기 300MB

하루 업로드 저장 용량:
500만 × 10% × 300MB = 150TB/일

CDN으로 영상을 서빙하면 비용이 큼
→ 비용 최적화가 핵심 이슈가 됨
```

## 기반 기술: 왜 직접 다 만들지 않는가

이 설계의 중요한 전제는 CDN과 클라우드 스토리지 같은 기존 서비스를 적극 활용한다는 것이다.

- **블롭 스토리지(Blob Storage)**: 아마존 S3 같은 대용량 객체 저장소. 원본 동영상과 변환된 동영상을 저장한다.
- **CDN(Content Delivery Network)**: 동영상을 전 세계 엣지 서버에 캐싱해 사용자와 가까운 곳에서 빠르게 전달한다.

동영상 스트리밍 인프라를 처음부터 만드는 건 엄청난 비용과 시간이 들고, 이미 검증된 클라우드 서비스가 있으므로 이를 활용하는 것이 현명하다.

## 개략적 설계

시스템은 크게 세 부분으로 나뉜다.

- **클라이언트**: 동영상을 보거나 올리는 단말(모바일, 웹, TV)
- **CDN**: 동영상 자체가 저장되어 스트리밍되는 곳. 사용자는 CDN에서 동영상을 받아본다.
- **API 서버**: 동영상 스트리밍을 제외한 나머지 모든 것. 피드 추천, 업로드 URL 생성, 메타데이터 갱신, 사용자 정보 등.

### 동영상 업로드 흐름

업로드는 두 개의 흐름이 병렬로 일어난다.

**흐름 A: 동영상 자체 업로드 및 변환**

```
① 사용자가 동영상 업로드
② 원본 동영상이 원본 저장소(original storage)에 저장됨
③ 트랜스코딩 서버가 원본을 가져와 변환(transcoding)
④ 변환 완료된 동영상들이 변환 저장소(transcoded storage)에 저장
⑤ 변환된 동영상이 CDN으로 전송됨
⑥ 트랜스코딩 완료 큐가 완료 이벤트를 알림
⑦ 완료 핸들러가 메타데이터 DB/캐시를 갱신
⑧ API 서버가 클라이언트에게 "업로드 및 변환 완료" 통보
```

**흐름 B: 메타데이터 갱신**

동영상이 업로드되는 동안, 파일의 메타데이터(제목, 설명, 크기, 업로더 등)를 메타데이터 DB와 캐시에 기록한다.

## 트랜스코딩(Transcoding)이란 — 이 설계의 핵심

동영상 인코딩/트랜스코딩은 이 시스템에서 가장 중요하고 무거운 작업이다.

### 왜 트랜스코딩이 반드시 필요한가

사용자가 올리는 원본 동영상은 그대로 재생하기에 부적합하다.

- **단말이 제각각이다**: 어떤 사람은 5G 폰으로, 어떤 사람은 느린 WiFi 노트북으로, 어떤 사람은 4K TV로 본다.
- **네트워크가 변한다**: 같은 사용자도 지하철에서는 느리고 집에서는 빠르다. 상황에 따라 화질을 바꿔야 끊김 없이 볼 수 있다.
- **호환성**: 단말과 브라우저마다 지원하는 코덱·포맷이 다르다.

그래서 원본 하나를 여러 해상도·비트레이트·포맷의 버전들로 미리 변환해둔다. 480p, 720p, 1080p, 4K 등으로 만들어두고, 재생 시 사용자의 상황에 맞는 버전을 골라 보낸다.

### DAG 기반 트랜스코딩 파이프라인

트랜스코딩은 단일 작업이 아니라 여러 단계의 조합이다. 사용자마다, 콘텐츠마다 필요한 처리가 다르다(어떤 건 워터마크가 필요하고, 어떤 건 썸네일 추출이 필요하고 등등). 이 유연성을 위해 **DAG(방향성 비순환 그래프, Directed Acyclic Graph) 모델**을 쓴다.

```
원본 동영상
   ↓
[분할(splitting)] — 영상을 여러 조각으로 나눔
   ↓
   ├→ [비디오 인코딩] → 여러 해상도로
   ├→ [썸네일 추출]
   ├→ [워터마크 추가]
   └→ [오디오 처리]
   ↓
[병합(merging)] — 처리된 것들을 합침
   ↓
변환 완료 동영상
```

DAG로 정의하면 각 단계를 조립하듯 구성할 수 있고, 독립적인 단계는 병렬로 처리할 수 있다.

### 트랜스코딩 아키텍처

- **전처리기(Preprocessor)**: 원본 동영상을 조각(GOP, Group of Pictures)으로 나누고, DAG를 생성한다. 캐싱도 담당한다.
- **DAG 스케줄러**: DAG를 단계별 작업으로 나눠 자원 관리자에게 넘긴다.
- **자원 관리자(Resource Manager)**: 작업을 어느 작업 서버에 배치할지 관리한다. 여러 큐(작업 큐, 서버 큐, 실행 큐)로 자원을 효율적으로 배분한다.
- **작업 서버(Task Workers)**: DAG의 실제 작업(인코딩, 썸네일, 워터마크 등)을 수행한다.
- **임시 저장소(Temporary Storage)**: 처리 중간 결과를 보관한다. 데이터 종류에 따라 메모리/디스크를 나눠 쓴다.

> 이 구조는 앞서 여러 번 본 **워커 큐 패턴**의 정교한 버전이다. 무거운 CPU 작업(인코딩)을 작업 서버로 분리하고, 큐로 결합을 끊고, 자원 관리자가 부하를 분산한다. 작업이 DAG로 표현될 만큼 복잡해진 형태다.

## 동영상 스트리밍 흐름

### 스트리밍 프로토콜

동영상은 파일을 통째로 다운로드한 뒤 재생하는 게 아니라, **조금씩 받으면서 재생(streaming)** 한다. 이를 위한 스트리밍 프로토콜이 있다.

- MPEG-DASH (Dynamic Adaptive Streaming over HTTP)
- Apple HLS (HTTP Live Streaming)
- Microsoft Smooth Streaming, Adobe HDS 등

공통 원리는 동영상을 작은 조각(chunk)으로 나눠 순차적으로 전송하는 것이다.

### 적응형 비트레이트 스트리밍(Adaptive Bitrate Streaming)

핵심 개념이다. 재생 중에 네트워크 상태를 감지해서 화질을 실시간으로 바꾼다.

```
네트워크 빠름 → 1080p 조각을 받아옴
갑자기 느려짐 → 다음 조각은 480p로 낮춰 받음 (끊김 방지)
다시 빨라짐  → 720p, 1080p로 올림
```

이것이 가능한 이유가 바로 트랜스코딩이다. 여러 화질 버전을 미리 만들어뒀기 때문에, 상황에 맞는 조각을 골라 이어붙일 수 있다. **트랜스코딩(쓰기 시점 준비)과 적응형 스트리밍(읽기 시점 선택)이 짝을 이루는 구조**다.

### CDN을 통한 전송

동영상은 CDN에서 스트리밍된다. 사용자와 지리적으로 가장 가까운 엣지 서버가 동영상을 전달하므로 지연시간이 짧다.

## 최적화

### 비용 최적화 (핵심 이슈)

CDN 비용이 매우 크기 때문에, 이 시스템에서는 비용 최적화가 중요한 주제다. 유튜브 콘텐츠는 **롱테일(long-tail) 분포**를 따른다. 소수의 인기 영상이 대부분의 조회수를 차지하고, 나머지 방대한 영상은 거의 안 보인다.

이 특성을 이용한다.

- **인기 영상만 CDN에 둔다**: 자주 보는 영상만 CDN에 캐싱하고, 안 보이는 영상은 저렴한 저장소에 둔다.
- **인기 없는 영상은 인코딩을 덜 한다**: 거의 안 보는 영상을 모든 화질로 변환해두는 건 낭비다.
- **지역별 배포**: 특정 지역에서만 인기 있는 영상은 그 지역 CDN에만 둔다.
- **CDN을 직접 구축**: 규모가 아주 커지면 자체 CDN을 만들어 비용을 절감한다(유튜브가 실제로 함).

> 앞서 뉴스 피드에서 "비활성 사용자에게 자원을 낭비하지 않는다", 검색 자동완성에서 "인기 검색어만 관리"한 것과 같은 발상이다. **모든 데이터를 똑같이 대하지 않고, 인기도에 따라 차등한다**는 원칙이 반복된다.

### 업로드 안정성 (재개 가능한 업로드)

1GB짜리 동영상을 업로드하다 중간에 네트워크가 끊기면? 처음부터 다시 올리는 건 끔찍하다. 그래서 파일을 여러 조각으로 나눠 업로드하고, 끊긴 지점부터 재개할 수 있게 한다.

### 안정성 확보

- **미리 서명된 업로드 URL(presigned upload URL)**: 인증된 사용자만 지정된 위치에 업로드하도록 보안을 유지한다. API 서버가 URL을 발급하면, 클라이언트는 그 URL로 직접 스토리지에 업로드한다.
- **동영상 보호(DRM, AES 암호화, 워터마킹)**: 저작권 보호를 위한 장치들.

### 에러 처리

- **복구 가능한 에러(특정 조각 트랜스코딩 실패)**: 몇 번 재시도하고, 계속 실패하면 클라이언트에 에러 반환.
- **복구 불가능한 에러(잘못된 포맷)**: 작업을 중단하고 에러 반환.

시스템 컴포넌트별로 장애 대응 전략을 둔다(업로드 서버 장애, 스플리팅 실패, DB 장애 등).

## 마무리: 추가로 논의할 점

- **API 계층의 규모 확장**: 무상태 서버로 만들어 수평 확장.
- **DB 계층의 규모 확장**: 다중화와 샤딩.
- **라이브 스트리밍**: 실시간 방송은 지연시간 요구가 훨씬 빡빡하고, 업로드와 스트리밍이 동시에 일어나므로 별도 설계가 필요하다. 다만 트랜스코딩과 스트리밍이라는 기본 원리는 공유한다.
- **콘텐츠 저작권 침해 감지**: 업로드된 영상이 저작권을 침해하는지 자동 감지(유튜브의 Content ID). 앞서 웹 크롤러에서 본 중복 콘텐츠 탐지와 비슷하게, 오디오/비디오 지문(fingerprint)을 만들어 비교한다.

## 정리

유튜브 설계의 본질은 두 가지다. **"거대한 동영상을 어떻게 저장·변환하는가"** 와 **"전 세계에 어떻게 끊김 없이 전달하는가"** 이다.

전자의 답은 **트랜스코딩**이다. 원본 하나를 여러 화질·포맷으로 미리 변환해두는 것으로, DAG 파이프라인과 워커 큐로 이 무거운 작업을 처리한다. 후자의 답은 **CDN + 적응형 비트레이트 스트리밍**이다. 미리 만들어둔 여러 화질 조각을, 사용자와 가까운 CDN에서, 네트워크 상황에 맞춰 골라 전달한다.

관통하는 원칙은 앞선 장들과 같다. 무거운 작업은 워커로 분리하고(알림 시스템), 큐로 결합을 끊고, 인기도에 따라 자원을 차등하며(뉴스 피드·자동완성), **읽기를 빠르게 하기 위해 쓰기 시점에 미리 준비한다**(트랜스코딩 = 뉴스 피드의 Push, 자동완성의 top-k 캐싱과 같은 철학). 유튜브는 이 원칙들이 "대용량 미디어"라는 맥락에서 총합된 사례다.
