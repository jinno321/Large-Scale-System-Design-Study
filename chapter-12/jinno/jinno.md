# 채팅 시스템 설계

WhatsApp, Instagram DM, Facebook Messenger, WeChat, Discord 등 채팅 시스템은 종류가 다양하다. 채팅 앱이라고 했을 때 사람들이 떠올리는 요구사항은 제각각이다. 각 시스템별로 요구사항과 중요하게 여기는 부분이 조금씩 다르므로, 요구사항을 명확히 정의하는 것이 아주 중요하다.

- **1:1 채팅에 집중하는 앱:** 위챗, 페이스북 메신저, 왓츠앱
- **업무용 앱:** 슬랙
- **게임 채팅:** 디스코드 (대규모 그룹 소통 및 낮은 응답 지연의 음성 채팅)

---

## 1. 요구사항 가정
* **채팅 형태:** 1:1 채팅과 그룹 채팅을 둘 다 지원해야 한다.
* **플랫폼:** 모바일 앱과 웹 앱을 지원해야 한다.
* **트래픽 규모:** DAU(Daily Active Users) 기준 5,000만 명을 처리할 수 있어야 한다.
* **그룹 채팅 인원:** 최대 100명까지 참여 가능
* **주요 기능:** 1:1 채팅, 그룹 채팅, 사용자 접속 상태 표시 지원
* **메시지 유형:** 텍스트 메시지만 가능 (100,000자 이하)

---

## 2. 개략적 설계안

채팅 시스템에서 가장 중요한 개념은 **클라이언트와 서버의 통신 방법**이다. 클라이언트(모바일 앱, 웹 앱)끼리 직접 통신하지 않고, 모든 기능(메시지 수신, 전달, 보관)을 지원하는 **채팅 서비스(서버)**를 거쳐 통신한다.

### 서버의 핵심 기능
* 클라이언트들로부터 메시지 수신
* 메시지 수신자 결정 및 전달
* 수신자가 오프라인일 경우 접속할 때까지 메시지 보관

---

### 통신 프로토콜 선택

#### 1) HTTP 프로토콜
* **메시지 전송:** HTTP의 `Keep-Alive` 헤더를 활용하면 TCP 핸드셰이크 횟수를 줄일 수 있어 메시지 전송 용도로는 괜찮은 선택이다. (페이스북 초기 채택)
* **메시지 수신:** HTTP는 클라이언트가 요청을 시작하는 단방향 프로토콜이므로, 서버가 임의 시점에 클라이언트에게 메시지를 전달하기 어렵다.

#### 2) 폴링 (Polling)
* 클라이언트가 주기적으로 서버에 새 메시지가 있는지 물어보는 방식이다.
* 자주 물어볼수록 비용이 증가하며, 답할 메시지가 없을 때도 서버 자원이 낭비된다.

#### 3) 롱 폴링 (Long Polling)
* 클라이언트는 새 메시지가 반환되거나 타임아웃될 때까지 연결을 유지한다.
* 메시지를 받으면 연결을 종료하고 다시 요청을 보낸다.
* **단점:** 메시지를 보내는 클라이언트와 받는 클라이언트가 서로 다른 채팅 서버에 연결되어 있을 수 있으며, 서버 입장에서 클라이언트의 연결 해제 여부를 알기 어렵다.

#### 4) 웹소켓 (WebSocket)
* 서버가 클라이언트에게 비동기 메시지를 보낼 때 가장 널리 사용하는 기술이다.
* 최초 연결 시 HTTP 핸드셰이크를 거쳐 웹소켓 연결로 업그레이드되며, 이후 **양방향 항구적 연결**이 유지된다.
* 80, 443 포트를 그대로 사용하므로 방화벽 환경에서도 잘 동작한다.
* 메시지 송수신에 동일한 프로토콜을 사용하므로 설계와 구현이 직관적이다.

---

### 전체 시스템 구조

시스템은 크게 세 부분으로 나눌 수 있다.

1. **무상태 서비스 (Stateless Services):** 로그인, 회원가입, 사용자 프로필 표시 등을 처리하는 전통적인 HTTP 요청/응답 서비스. 로드밸런서 뒤에 위치한다.
2. **상태 유지 서비스 (Stateful Services):** 채팅 서비스가 이에 해당한다. 클라이언트가 독립적인 네트워크 연결(웹소켓)을 계속 유지해야 하므로 상태 유지가 필요하다.
3. **제3자 서비스 연동 (Third-party Integration):** 앱이 실행 중이지 않을 때 새 메시지 알림을 보내기 위한 **푸시 알림 서비스(APNS, FCM)** 연동이 필수적이다.

---

### 저장소 선택 (RDBMS vs NoSQL)

채팅 시스템이 다루는 데이터는 크게 두 가지 유형이다.

1. **일반 데이터 (프로필, 설정, 친구 목록):** 데이터의 신뢰성과 안정성을 보장하는 **관계형 데이터베이스(RDBMS)**에 저장한다. 가용성과 규모 확장을 위해 다중화(Replication)와 샤딩(Sharding)을 적용한다.
2. **채팅 이력 데이터:** 읽기:쓰기 비율이 대략 **1:1**이며, 최근 메시지가 주로 조회되지만 무작위 검색도 일어난다. 데이터 양이 매우 방대하다.

> **결론:** 채팅 이력 보관에는 **키-값 저장소(NoSQL)**가 적합하다.
> - 수평적 규모 확장(Horizontal Scaling)이 매우 쉽다.
> - 데이터 접근 지연 시간(Latency)이 매우 낮다.
> - RDBMS는 긴 꼬리(Long-tail) 데이터 접근 및 인덱싱 비용 처리에 불리하다.

#### 데이터 모델
* **1:1 채팅 테이블:** `{message_id, message_from, message_to, content, created_at}`
* **그룹 채팅 테이블:** `{channel_id, message_id, message_from, content, created_at}`
  * `(channel_id, message_id)`의 복합키를 기본 키(Primary Key)로 사용한다.
  * `channel_id`는 파티션 키(Partition Key)로 사용하여 특정 채널 대상 질의를 최적화한다.

---

### 메시지 ID (Message ID)
메시지 ID는 **고유성(Unique)**과 **시간 순서 정렬 가능성(Sortable by time)**을 만족해야 한다.

* NoSQL은 RDBMS의 `auto_increment` 기능을 제공하지 않는다.
* 스노우플레이크(Snowflake) 같은 전역 ID 생성기를 사용할 수도 있지만, 채팅 시스템에서는 채팅방(채널) 내에서만 순서가 보장되면 충분하다.
* 따라서 `channel_id`나 `chat_id` 범위 내에서 동작하는 **지역적 순서 번호 생성기(Local Sequence Generator)**를 사용하는 것이 훨씬 효율적이다.

## 3. 상세 설계

### 1) 서비스 탐색 (Service Discovery)
수많은 채팅 서버 중 클라이언트에게 최적의 서버를 할당하기 위해 **서비스 탐색(Service Discovery)** 솔루션(예: Apache ZooKeeper)을 활용한다.

1. 클라이언트가 로그인 서비스(무상태)를 통해 인증을 마친다.
2. 서비스 탐색 기능이 클라이언트의 위치, 서버 부하 등을 고려해 최적의 채팅 서버(예: Chat Server 2)를 선택한다.
3. 클라이언트에게 해당 채팅 서버의 IP/Port 정보를 반환한다.
4. 클라이언트는 해당 채팅 서버와 웹소켓 연결을 맺는다.

---

### 2) 메시지 흐름 (Message Flow)

#### 1:1 채팅 메시지 처리 흐름
1. 클라이언트 A가 채팅 서버 1로 메시지를 전송한다.
2. 채팅 서버 1은 ID 생성기를 통해 메시지 ID를 발급받는다.
3. 채팅 서버 1은 해당 메시지를 메시지 동기화 큐(Message Sync Queue)로 보낸다.
4. 메시지가 키-값 저장소에 저장된다.
5. 수신자(클라이언트 B)의 접속 상태에 따라 처리가 갈린다.
   - **B가 온라인인 경우:** B가 연결된 채팅 서버 2로 메시지가 전달되어 웹소켓으로 실시간 전송된다.
   - **B가 오프라인인 경우:** 푸시 알림 서비스(APNS/FCM)를 통해 알림을 보낸다.

#### 그룹 채팅 메시지 처리 흐름
A가 메시지를 보내면 그룹 내 다른 사용자(B, C 등)의 **메시지 수신함(In-box)**에 각각 메시지를 복사한다 (**Message Fan-out** 기법).
* 수신자 관점에서는 자기 수신함만 조회하면 되므로 읽기 작업이 단순해진다.
* 본 설계안은 **그룹 인원이 최대 100명**으로 제한되어 있으므로 쓰기 시점 복사(Fan-out on write) 방식을 적용하기에 적합하다.

---

### 3) 접속 상태 표시 (Presence Indicator)

접속 상태 서버(Presence Server)는 웹소켓 연결을 통해 사용자의 온라인/오프라인 상태를 관리한다.

#### 로그인 / 로그아웃
* **로그인:** 클라이언트와 웹소켓 연결이 맺어지면 상태를 `Online`으로 변경한다.
* **로그아웃:** 클라이언트가 로그아웃하면 웹소켓 연결이 끊기고 상태를 `Offline`으로 변경한다.

#### 접속 장애 (Heartbeat)
네트워크가 불안정하여 웹소켓 연결이 일시적으로 끊길 때마다 상태를 변경하면 화면 껌벅임 등 사용자 경험이 나빠진다.
* 이를 해결하기 위해 **박동(Heartbeat) 메커니즘**을 사용한다.
* 클라이언트는 주기적(예: 5초마다)으로 박동 이벤트를 전송하고, 서버가 일정 시간(예: 30초) 동안 이벤트를 받지 못하면 그제야 `Offline`으로 전환한다.

#### 상태 정보 전파
* **소규모 그룹/친구:** 발행-구독 모델(Pub/Sub)을 통해 A의 접속 상태 변경 이벤트를 친구들의 채널로 전파한다.
* **대규모 그룹:** 과도한 트래픽을 방지하기 위해 사용자가 채팅방에 입장하거나 리프레시할 때 수동으로 상태를 조회(Pull)하도록 설계한다.

## 4. 정리 및 추가 고려사항

### 요약
1. **프로토콜:** 실시간 통신은 **웹소켓(WebSocket)**, 기타 기능은 **HTTP** 사용.
2. **규모 확장성:** **서비스 탐색(ZooKeeper)**을 이용해 로드밸런싱 및 채팅 서버 할당.
3. **저장소:** 일반 데이터는 **RDBMS**, 대규모 채팅 이력은 **키-값 저장소(NoSQL)**에 보관.
4. **접속 상태:** **Heartbeat** 및 **Pub/Sub** 모델을 적용하여 실시간 상태 관리.

### 추가 논의 주제
* **미디어 파일 전송:** 이미지/동영상은 용량이 크므로 S3 등 객체 저장소 업로드, 썸네일 생성, CDN 연동을 고려해야 한다.
* **종단간 암호화 (End-to-End Encryption):** 메시지 송수신자 외에는 서버조차 메시지 내용을 볼 수 없도록 처리하는 보안 기술.
* **클라이언트 캐싱:** 로컬 디스크에 읽은 메시지를 캐싱하여 서버 요청 축소 및 앱 로딩 속도 개선.
* **오류 처리:** 메시지 전송 실패 시 재시도 로직 및 Sequence Number 기반 메시지 순서 재정렬 알고리즘 도입.
