# 채팅 시스템(Chat System) 설계

## 채팅 시스템이란

사용자끼리 실시간으로 메시지를 주고받는 시스템. 페이스북 메신저, 위챗, 왓츠앱, 디스코드, 슬랙 등이 해당한다.

채팅 앱마다 기능이 다르므로, 설계 전에 어떤 종류의 채팅을 만들지 명확히 하는 것이 특히 중요하다. 1:1 채팅에 집중하는 앱과 대규모 그룹 채팅에 집중하는 앱은 설계가 완전히 달라지기 때문이다.

## 문제 이해 및 설계 범위 확정

질문을 통해 요구사항을 확정한다.

- 어떤 앱? 1:1 전용인가 그룹 채팅인가? 둘 다 지원한다.
- 모바일 앱인가 웹인가? 둘 다.
- 처리 규모는? DAU 5,000만 명
- 그룹 인원 제한은? 최대 100명
- 중요한 기능은? 1:1 채팅, 그룹 채팅, 사용자 접속 상태(presence) 표시, 멀티 디바이스 지원, 푸시 알림
- 메시지 크기 제한은? 텍스트 100,000자 이하
- 종단 간 암호화(E2E encryption)가 필요한가? 지금은 필수 아님(추후 논의)
- 채팅 이력은 얼마나 저장하나? 영원히

## 채팅 시스템의 근본 문제: 서버가 클라이언트에게 어떻게 먼저 말을 거나

채팅의 핵심 난제는 **"상대방이 보낸 메시지를 내가 어떻게 실시간으로 받는가"** 이다.

HTTP는 클라이언트가 요청해야만 서버가 응답하는 구조다. 그런데 채팅에서는 서버가 먼저 클라이언트에게 "새 메시지 왔어"라고 알려야 한다. 이 문제를 푸는 방식이 여럿 있고, 채팅 시스템 설계의 출발점이 된다.

> 앞서 푸시 알림에서 다룬 push vs pull 문제와 정확히 같은 맥락이다. 다만 채팅은 알림보다 훨씬 빈번하고 양방향이라 요구사항이 더 까다롭다.

### 폴링(Polling)

클라이언트가 주기적으로 "새 메시지 있어?"라고 물어본다.

```
클라이언트: 새 거 있어? → 서버: 없어
(10초 후 반복)
```

단점: 대부분의 요청이 헛수고다. 자주 물으면 서버 부하가 크고, 드물게 물으면 메시지가 늦게 온다.

### 롱 폴링(Long Polling)

클라이언트가 물어보면, 서버가 답이 생길 때까지 응답을 붙잡고 기다린다. 새 메시지가 생기거나 타임아웃이 되면 그때 응답한다. 응답을 받으면 클라이언트는 즉시 다시 요청한다.

단점:
- 메시지 발신자와 수신자가 같은 서버에 연결되지 않을 수 있다. HTTP 서버는 보통 무상태라 라운드 로빈으로 분배되기 때문이다.
- 서버는 클라이언트가 연결을 끊었는지 알기 어렵다.
- 여전히 비효율적이다. 메시지를 안 받는 사용자도 계속 주기적으로 연결한다.

### 웹소켓(WebSocket) — 채택

서버가 클라이언트에게 비동기적으로 메시지를 보낼 때 가장 널리 쓰이는 해법이다.

웹소켓은 양방향 지속 연결이다. 클라이언트가 한 번 연결을 열면, 그 연결이 계속 유지되면서 양쪽 어느 쪽이든 언제든 데이터를 보낼 수 있다.

```
일반 HTTP:  요청 → 응답 → 연결 종료 (매번 반복)

웹소켓:     연결 수립(handshake) → 연결 유지
            ↓↑ ↓↑ ↓↑  (양방향으로 자유롭게)
```

- HTTP 연결로 시작해서 핸드셰이크를 거쳐 웹소켓 연결로 업그레이드된다.
- 방화벽이 있는 환경에서도 잘 동작한다(80, 443 포트 사용).
- 발신과 수신 모두 같은 웹소켓 연결 위에서 이루어진다.

이 덕분에 서버가 새 메시지를 클라이언트에게 즉시 밀어 넣을 수 있다.

### 웹소켓 연결은 언제 설정되나

보통 **로그인 직후**다. 채팅방 화면을 여는 시점이 아니다.

이유는 로그인만 하면 "언제든 누구에게서든" 메시지가 올 수 있기 때문이다. 채팅방을 안 보고 있어도 받아야 하는 것들이 있다 — 다른 방에서 온 새 메시지, 안 읽은 메시지 배지 카운트, 친구의 온라인/오프라인 상태 변화, 타이핑 인디케이터 등.

```
1. 로그인 (무상태 서비스에서 인증)
2. 서비스 탐색이 최적 채팅 서버 주소를 반환
3. 그 서버와 웹소켓 연결 수립  ← 여기서 연결됨
4. presence 서버가 상태를 online으로 기록 (연결 수립 = 온라인 판정 근거)
5. 이후 어느 화면에 있든 이 연결로 메시지를 받음
```

즉 **"웹소켓 연결이 곧 온라인"** 이다. presence 표시가 연결 수립/해제와 묶여 있는 이유가 이것이다.

반면 채팅방을 여는 시점에 일어나는 건 연결이 아니라, 그 방의 과거 메시지 이력을 불러오는 것(HTTP 조회)이다.

단, 모바일은 배터리 때문에 앱이 백그라운드로 가면 연결을 끊고 푸시 알림으로 전환한다.

### 양방향이 "필수"인가

엄밀히 말하면 양방향이 필수는 아니다. 보내기는 내가 능동적으로 하는 행위라 HTTP 요청 한 번 보내면 되고, 받기만 서버가 밀어줘야(push) 한다. 이론상 SSE(받기) + POST(보내기) 조합으로도 채팅을 만들 수 있다.

웹소켓이 채택되는 진짜 이유는 "양방향이어야만 해서"가 아니라, **보내기·받기를 연결 하나로 합칠 수 있어서**다. 채팅은 발신도 꽤 빈번하고(타이핑 신호까지 포함) 저지연이 중요한데, 이럴 때 매번 새 POST 요청을 여는 것보다 이미 열린 연결로 흘려보내는 게 효율적이다.

```
타이핑 인디케이터: 키를 누를 때마다 "입력 중" 신호
  → POST면 타이핑 한 번에 요청 수십 개
  → 웹소켓이면 열린 연결로 가볍게 흘려보냄
```

### 웹소켓의 단점

웹소켓이 만능은 아니다. 대가가 따른다.

- **상태 유지로 인한 확장의 어려움**: 서버가 "누가 어느 연결에 붙어 있는지"를 계속 들고 있어야 한다. 서로 다른 서버에 붙은 두 사용자가 대화하려면 서버 간 메시지 중개(Redis pub/sub 등)가 별도로 필요하다.
- **연결 유지 비용**: 수백만 동시 접속이면 연결 관리 자체가 큰 부담이다. NAT이 유휴 연결을 끊어버리므로 주기적으로 keepalive(핑/퐁)를 보내야 하고, 모바일에서는 배터리를 소모한다.
- **로드밸런서/프록시 호환성**: 일부 오래된 프록시나 방화벽은 웹소켓의 프로토콜 업그레이드를 제대로 처리하지 못한다. 실무에서는 웹소켓을 시도하고 실패하면 롱폴링으로 자동 강등하는 폴백을 함께 둔다.
- **재연결 처리를 직접 해야 함**: SSE는 자동 재연결과 `Last-Event-ID` 기반 재개가 표준에 내장돼 있지만, 웹소켓은 재연결과 놓친 메시지 동기화를 애플리케이션이 직접 구현해야 한다. (뒤에 나오는 `cur_max_message_id`가 이 역할을 한다.)
- **로드밸런싱이 까다로움**: 같은 사용자의 연결이 계속 같은 서버로 가야 하므로, 일반적인 라운드 로빈 대신 sticky session이나 연결 라우팅 로직이 필요하다.

## 개략적 설계

### 무상태 서비스 vs 상태 유지 서비스

시스템을 세 부분으로 나눠서 본다.

**무상태 서비스(stateless services)**

로그인, 회원가입, 사용자 프로필 표시 등 전통적인 요청-응답 서비스. 로드밸런서 뒤에 두고 수평 확장한다. 이 중 **서비스 탐색(service discovery)** 이 중요한데, 클라이언트가 접속할 채팅 서버의 DNS 호스트명을 알려주는 역할을 한다.

**상태 유지 서비스(stateful service)**

채팅 서비스가 유일한 상태 유지 서비스다. 각 클라이언트가 채팅 서버와 웹소켓 지속 연결을 유지하기 때문이다.

> 왜 채팅 서비스만 상태를 유지하나? 웹소켓 연결 자체가 상태다. "111번 사용자가 지금 A서버에 연결되어 있다"는 정보를 서버가 들고 있어야, 그 사용자에게 온 메시지를 A서버로 보낼 수 있다. 이 연결 정보는 특정 서버에 묶여 있어서, 무상태 서비스처럼 아무 서버나 요청을 받게 할 수 없다.

**제3자 연동(푸시 알림)**

앱이 실행 중이지 않을 때 메시지 도착을 알리려면 푸시 알림이 필요하다. 앞서 설계한 알림 시스템이 여기 연동된다.

### 저장소: 어떤 DB를 쓸 것인가

데이터는 두 종류다.

**1. 일반 데이터 (사용자 프로필, 설정, 친구 목록)**

관계형 DB에 저장한다. 안정적이고, 다중화·샤딩으로 확장한다.

**2. 채팅 이력 데이터 (메시지)**

이게 핵심이다. 양이 어마어마하다.

```
데이터 특성:
- 양이 엄청나게 많다 (페이스북 메신저는 하루 600억 건)
- 최근 메시지만 자주 조회된다 (오래된 건 거의 안 봄)
- 랜덤 액세스(검색)가 필요하다
- 읽기:쓰기 비율이 1:1에 가깝다
```

이런 특성 때문에 **키-값 저장소(NoSQL)** 를 추천한다. 페이스북 메신저는 HBase, 디스코드는 카산드라를 쓴다.

> **왜 채팅에 키-값 저장소인가?**
> - 수평 확장이 쉽다: 관계형 DB는 일정 규모를 넘으면 확장이 고통스럽다.
> - 낮은 지연시간: 키로 바로 접근하므로 빠르다.
> - 접근 패턴에 맞다: 채팅은 "이 대화방의 메시지들을 시간순으로"라는 단순한 접근이 대부분이다. 복잡한 JOIN이 필요 없다.
>
> 앞서 6장에서 설계한 분산 키-값 저장소가 여기서 실제로 쓰이는 셈이다. 카산드라는 그 장에서 다룬 안정 해시·정족수·가십 프로토콜을 실제로 구현한 시스템이다.

### 메시지 ID 생성

메시지의 순서를 알려면 각 메시지에 **정렬 가능한 유일 ID**가 필요하다.

```
요구사항:
- 유일해야 한다
- 시간순으로 정렬 가능해야 한다 (ID가 클수록 최신)
```

이 요구사항은 앞서 7장에서 다룬 유일 ID 생성기와 정확히 같다. auto_increment는 여러 서버 환경에서 안 되므로, 스노플레이크 같은 방식을 쓰거나, 한 채팅방 안에서만 유일하면 되는 경우 지역적 순번(local sequence)을 쓸 수도 있다.

## 상세 설계

### 서비스 탐색(Service Discovery)

클라이언트가 접속하기에 가장 적합한 채팅 서버를 골라주는 역할이다. 기준은 지리적 위치, 서버의 부하 등이다. 아파치 주키퍼(Zookeeper) 같은 도구가 흔히 쓰인다.

```
1. 사용자가 로그인
2. 서비스 탐색이 최적 채팅 서버를 선택 (예: 서버2)
3. 사용자에게 서버2의 주소를 반환
4. 사용자가 서버2와 웹소켓 연결 수립
```

### 1:1 채팅 메시지 흐름

```
사용자 A ──웹소켓──→ 채팅 서버1
                        ↓
                    ① ID 생성기로 메시지 ID 발급
                    ② 메시지를 메시지 동기화 큐에 넣음
                    ③ 키-값 저장소에 메시지 저장
                        ↓
            사용자 B가 온라인인가?
              ├─ 온라인: 채팅 서버2(B가 연결된)로 전달 → 웹소켓으로 B에게 push
              └─ 오프라인: 푸시 알림 서버로 보냄
```

핵심은 A와 B가 서로 다른 채팅 서버에 연결되어 있을 수 있다는 점이다. 서버1은 B가 어느 서버에 붙어 있는지 알아내서 그 서버로 메시지를 넘겨야 한다.

### 여러 기기 간 메시지 동기화

한 사용자가 폰과 노트북을 동시에 쓸 수 있다. 모든 기기의 메시지가 일치해야 한다.

각 기기는 `cur_max_message_id` 라는 변수를 유지한다. 그 기기가 받은 가장 최신 메시지의 ID다.

```
동기화 방법:
- 서버의 최신 메시지 ID > 기기의 cur_max_message_id
  → 그 사이의 메시지들을 해당 기기로 전송
```

새 기기로 로그인하거나 오프라인이었던 기기가 다시 붙으면, 이 값을 기준으로 놓친 메시지를 받아온다.

### 그룹 채팅 흐름

그룹 채팅의 설계 포인트는 "메시지를 어떻게 여러 명에게 전달하는가"이다.

**발신자 입장 (쓰기 시 팬아웃)**

```
사용자 A가 그룹에 메시지 전송
  ↓
A의 메시지가 각 수신자(B, C)의 "메시지 동기화 큐"에 복사됨
  ↓
각 수신자는 자기 큐에서 메시지를 받음
```

메시지 동기화 큐를 **"수신자별 받은 편지함"** 으로 생각하면 된다.

이건 11장 뉴스 피드의 팬아웃(fanout)과 같은 발상이다. 쓰기 시점에 각 수신자의 큐로 복사해두는 것이다.

이 방식의 장단점:
- **장점**: 수신자는 자기 큐만 보면 되므로 메시지 동기화가 간단하다. 그룹이 작을 때(100명 이하) 효율적이다.
- **단점**: 그룹이 매우 크면 메시지 하나가 수많은 큐로 복사되어 비싸진다.

> 그룹 인원 제한(100명)을 요구사항에서 확정한 게 여기서 의미를 갖는다. 왓츠앱이 그룹 상한을 두는 이유가 바로 이 팬아웃 비용 때문이다. 만약 인원 제한이 없다면 뉴스 피드처럼 push/pull 하이브리드를 고민해야 했을 것이다.

**수신자 입장**

한 수신자는 여러 그룹으로부터 메시지를 받으므로, 각 메시지가 어느 그룹 것인지 구분할 수 있어야 한다. 수신자의 받은 편지함(메시지 동기화 큐)이 여러 발신자·그룹의 메시지를 모은다.

### 접속 상태(Presence) 표시

"온라인/오프라인" 표시는 별도의 **접속 상태 서버(presence servers)** 가 웹소켓으로 관리한다.

**로그인 시**

```
사용자가 웹소켓 연결 수립
  → presence 서버가 상태를 online으로 기록
  → user_id에 last_active_at 타임스탬프 갱신
```

**로그아웃 시**

명시적으로 로그아웃하면 상태를 offline으로 바꾼다.

**접속 장애 (핵심 문제)**

인터넷이 끊겼다 붙었다 하면, 그때마다 online/offline을 번쩍이면 사용자 경험이 나쁘다.

이를 해결하기 위해 **박동(heartbeat) 메커니즘** 을 쓴다.

```
온라인 클라이언트가 주기적으로 heartbeat를 presence 서버에 보냄
  ↓
마지막 heartbeat로부터 x초(예: 30초) 안에 다음 heartbeat가 오면
  → 계속 online 유지
  ↓
x초가 지나도 heartbeat가 없으면
  → offline으로 전환
```

> 6장 분산 키-값 저장소에서 장애 감지에 쓴 박동 카운터(heartbeat)와 같은 아이디어다. "일정 시간 신호가 없으면 죽은 것으로 간주"하는 패턴이 여기서도 재사용된다. 순간적인 네트워크 끊김에 과민 반응하지 않도록 임계 시간을 두는 것이 핵심이다.

**상태 전파(Presence Fanout)**

친구 관계를 publish-subscribe 모델로 관리한다. 각 친구 쌍마다 채널을 두고, 상태가 바뀌면 그 채널을 구독한 친구들에게 알린다. 다만 친구가 매우 많으면 이것도 비용이 크므로, 사용자가 특정 그룹에 들어갔을 때만 그 그룹 멤버의 상태를 조회하는 식으로 최적화하기도 한다.

## 마무리: 추가로 논의할 점

- **미디어 지원**: 사진, 비디오는 텍스트보다 크다. 압축, 클라우드 저장, 썸네일 등을 고려해야 한다.
- **종단 간 암호화(E2E encryption)**: 왓츠앱처럼 발신자와 수신자만 메시지를 읽을 수 있게 한다. 서버조차 내용을 못 본다.
- **캐싱**: 클라이언트 측에 이미 받은 메시지를 캐시해두면 서버와의 데이터 전송량을 줄일 수 있다.
- **로딩 속도 개선**: 사용자 데이터, 채널 등을 지역적으로 분산하는 네트워크를 구축(예: 슬랙).
- **에러 처리**:
  - 채팅 서버 장애: 채팅 서버 하나가 죽으면, 서비스 탐색이 새 서버를 배정해 클라이언트가 재연결하게 한다.
  - 메시지 재전송: 재시도(retry)와 큐(queue)로 메시지 전달을 보장한다.

## 정리

채팅 시스템의 근본 문제는 **"서버가 클라이언트에게 어떻게 먼저 실시간으로 말을 거는가"** 이고, 답은 **웹소켓 양방향 지속 연결**이다. 이 지속 연결 때문에 채팅 서버는 상태 유지 서비스가 되고, 그것이 확장을 까다롭게 만드는 핵심 요인이다.

나머지는 앞선 장들의 재조합이다. 메시지 저장에는 6장의 분산 키-값 저장소(카산드라)를, 메시지 ID에는 7장의 유일 ID 생성기를, 그룹 메시지 전달에는 11장의 팬아웃을, 접속 상태 감지에는 6장의 박동 메커니즘을, 오프라인 알림에는 10장의 알림 시스템을 가져다 쓴다. 채팅 시스템은 지금까지 배운 부품들이 거의 총출동하는 종합 설계에 가깝다.
