# 15장. 구글 드라이브와 같은 파일 저장소 서비스 설계

이번 장에서는 구글 드라이브, 드롭박스 같은 클라우드 서비스를 설계해본다. 이런 서비스는 파일 저장 및 동기화 서비스로, 문서, 사진, 비디오 같은 파일들을 클라우드에 보관하고 여러가지 단말에서 이용할 수 있는 서비스이다.

---

## 설계 범위

- 파일 업로드/다운로드, 파일 동기화, 알림
- 모바일 앱, 웹 앱 듀얼 지원
- 파일 암호화
- 10GB 파일 제한
- DAU 천만명

이번 장에서 설계에 집중할 기능들은 다음과 같다.

- 파일 추가 → 드래그 앤 드롭 방법
- 파일 다운로드
- 여러 단말 파일 동기화
- 파일 갱신 이력 조회
- 파일 공유
- 파일 편집, 삭제, 공유 시 알림 표시

> 구글 문서와 같은 협업 편집 기능은 논의하지 않는다.

---

# 개략적 설계안

이번에는 개략적 설계를 하는 것보다, 모든 것을 담은 한 대의 서버에서 출발해 서서히 천만 사용자 지원이 가능한 시스템으로 발전시켜 나가겠다.

### 초기 구성

- 파일을 올리고 다운로드 하는 과정을 처리할 웹 서버
- 사용자 데이터, 로그인 정보, 파일 정보 등 메타데이터를 보관할 데이터베이스
- 파일을 저장할 저장소 시스템 (1TB 공간 사용)

간단하게 아파치 웹 서버를 설치하고, MySQL 데이터베이스를 깔고 그 밑에 `drive/` 라는 하위 디렉터리들을 두고 이곳에 업로드되는 파일들을 저장하면 된다.

또한 기본적으로 세 가지 API가 필요하다.

- 파일 업로드
- 파일 다운로드
- 파일 갱신 히스토리 제공

### 파일 업로드 종류

파일 업로드에서는 2가지 종류의 업로드를 지원하면 된다.

#### 1. 단순 업로드

파일 전체를 한 번에 업로드하는 방식

#### 2. 이어올리기(Resumable Upload)

파일 사이즈가 크고 네트워크 문제로 업로드가 중단될 가능성이 높을 때 사용하는 방식

# 한 대 서버의 제약 극복

결국 업로드되는 파일이 많아지면 파일 시스템은 가득 찬다.

가장 쉬운 방법은 데이터 샤딩으로 여러 서버에 나누어 저장하는 것이다.

그렇게 하면 급한 불은 껐지만, 그래도 서버에 장애가 생기면 데이터를 잃게 되는 것은 여전히 걱정된다.

그래서 취할 수 있는 방법은 아마존 S3와 같은 외부 저장소이다.

이곳에서 다중화를 지원하며, 같은 지역 뿐만 아니라 여러 지역에 걸쳐 다중화를 할 수도 있으니, 데이터 손실을 막고 가용성도 최대한 보장할 수 있다.

S3에 넣고 나니 데이터 손실 걱정은 없다.

미래 개선점을 좀 더 찾아보면 다음과 같다.

### 로드밸런서

- 네트워크 트래픽을 고르게 분산
- 특정 웹 서버 장애 시 자동 우회

### 웹 서버

- 로드밸런서 추가 후 웹 서버 수평 확장 가능

### 메타데이터 데이터베이스

- SPOF 제거를 위해 파일 저장 서버와 분리

### 파일 저장소

- S3와 같은 저장소 사용
- 두 지역 이상에 다중화하여 가용성과 데이터 무손실 보장

---

# 동기화 충돌

가장 재밌으며, 가장 중요한 문제라고 생각한다.

구글 드라이브 같은 대형 저장소 시스템의 경우 동기화 충돌이 발생할 수 있다.

사실 APIdog 같은거 사용하거나, Git 같은 곳에서도 이러한 방법을 쓴다.

먼저 처리되는 변경은 성공한 것으로 보고, 나중에 처리되는 변경은 충돌이 발생한 것으로 표시시키는 것이다.

이렇게 되면 나중에 바꾼 사용자는

- 두 파일을 하나로 합칠지
- 둘 중 하나를 다른 파일로 대체할지

결정하면 된다.

# 개략적 설계안 (확장)

조금 새로운 것만 알아보자.

### 블록 저장소 서버

파일 블록을 클라우드 저장소에 업로드하는 서버다.

블록 저장소는 블록 수준 저장소라고도 하며, 클라우드 환경에서 데이터 파일을 저장하는 기술이다.

이 저장소는 파일을 여러 개의 블록으로 나눠 저장하며, 각 블록에는 고유한 해시값이 할당된다.

그리고 해시값은 메타데이터 데이터베이스에 저장된다.

각 블록은 독립적인 객체로 취급되며 클라우드 저장소 시스템에 보관된다.

### 아카이빙 저장소

오랫동안 사용되지 않은 비활성 데이터를 저장하기 위한 컴퓨터 시스템이다.

### 오프라인 사용자 백업 큐

클라이언트가 오프라인이어서 파일의 최신 상태를 확인할 수 없을 때는 해당 정보를 이 큐에 두어 나중에 클라이언트가 접속했을 때 동기화될 수 있도록 한다.

---

# 상세 설계

## 블록 저장소 서버

블록 저장소 서버를 좀 더 자세하게 파헤쳐 보자.

만약 파일이 업데이트 되는데 파일이 크다면, 이걸 전체를 서버로 보내면 네트워크 대역폭을 많이 잡아먹게 된다.

그래서 이를 위한 두 가지 기술 정도가 있다.

### 델타 동기화

파일이 수정되면 전체 파일 대신 수정이 일어난 블록만 동기화하는 것

### 압축

블록 단위로 압축해 두어 데이터 크기를 줄이는 것

---

클라이언트가 보낸 파일을 블록 단위로 나누고, 각 블록에 압축 알고리즘을 적용해야 하고, 암호화까지 한다.

새 파일이 추가된다면 블록 저장소 서버에서는

1. 주어진 파일을 작은 블록들로 분할
2. 각 블록 압축
3. 암호화 수행
4. 클라우드 저장소 업로드

---

## 강한 일관성

이 시스템에서 중요한 점 중 하나는 강한 일관성 모델을 기본으로 지원해야 하는 것이다.

같은 파일이 단말이나 사용자에 따라 다르게 보이면 안된다는 뜻이다.

메타데이터 캐시와 DB 계층에도 이 원칙이 기본이다.

메모리 캐시는 보통 결과적 일관성 모델을 지원한다.

- 캐시에 보관된 사본과 데이터베이스 원본이 일치
- DB 원본 변경 시 캐시 사본 무효화

RDB는 ACID를 보장하므로 강한 일관성을 보장하기 쉽다.

반면 NoSQL 같은 경우는 동기화 로직 안에 프로그램해 넣어야 한다.

그래서 여기서는 **RDB를 채택해서 일관성을 지키기로 한다.**

# 업로드 절차 & 다운로드 절차

## 업로드 절차

사용자가 파일을 업로드할 때는 크게 두 가지 요청이 병렬적으로 이루어진다.

- 파일 메타데이터 추가
- 파일 업로드

---

## 다운로드 절차

다운로드 절차에서 중요한 사실은 클라이언트가 다른 클라이언트가 파일을 편집하거나 추가했다는 사실을 감지하는 방법이다.

여기서 2가지 방법 정도가 있다.

### 방법 1

클라이언트 A가 접속 중이고 다른 클라이언트가 파일을 변경하면

알림 서비스가 클라이언트 A에게

> 변경이 발생했으니 새 버전을 끌어가야 한다

고 알려준다.

### 방법 2

클라이언트 A가 오프라인이면 데이터는 캐시에 보관되고,

해당 클라이언트의 상태가 접속 중으로 바뀌면 그때 새 버전을 가져간다.

---

파일이 변경됨을 감지한 클라이언트는

1. API 서버를 통해 메타데이터 조회
2. 블록 다운로드
3. 파일 재구성

순서로 동작한다.

---

# 알림 서비스

앞서 설계안에서 말했던 점처럼 알림 서비스에는 두 가지 정도 방법이 있다.

- 롱 폴링(Long Polling)
- 웹소켓(WebSocket)

본 설계안에서는 **롱 폴링**을 사용할 것이다.

### 이유

채팅 서비스와는 달리

- 양방향 통신이 필요하지 않다.
- 단시간에 많은 양의 데이터를 보낼 일도 없다.

---

# 저장소 공간 절약

파일 갱신 이력을 보존하고 안정성을 보장하기 위해서는 파일의 여러 버전을 여러 데이터센터에 보관할 필요가 있다.

그런 상황에서 모든 버전을 자주 백업하게 되면 저장용량이 너무 빨리 소진될 가능성이 있다.

이런 비용을 절감하기 위해 다음과 같은 전략을 사용한다.

### 중복 제거(Deduplication)

계정 차원에서 중복된 파일 블록을 제거한다.

- 해시값 활용

### 지능적 백업 전략

- 버전 수 한도 설정
- 중요한 버전만 보관

### 아카이빙 저장소 활용

몇 달 혹은 수년간 이용되지 않은 데이터는 아카이빙 저장소로 이동한다.

---

# 핵심 정리

- 초기에는 웹 서버 + DB + 파일 시스템으로 시작
- 저장소 부족 문제는 샤딩과 S3로 해결
- 로드밸런서와 DB 분리로 SPOF 제거
- 파일은 블록 단위 저장
- 블록마다 해시값 부여
- 델타 동기화와 압축으로 네트워크 비용 절감
- 강한 일관성을 위해 RDB 채택
- 충돌 발생 시 먼저 처리된 변경을 우선 적용
- 오프라인 사용자는 백업 큐를 통해 동기화
- 알림 서비스는 롱 폴링 사용
- 저장소 비용 절감을 위해 중복 제거, 버전 관리, 아카이빙 저장소 활용
