두 문서 모두 같은 스터디(8주차, 13장 - 검색어 자동완성 시스템) 노트고, 신선영님 자료는 간결한 요약형, 김보배님 자료는 Q&A 형식이 추가되고 더 상세합니다. 내용은 거의 동일해서 통합 정리하면:

## 1단계: 요구사항 & 규모 추정

**요구사항**

- 응답속도 100ms 이내
- 연관성 있는 검색어 반환
- 인기도 기반 정렬
- 규모 확장성 + 고가용성

**범위 확정**

- 접두어는 검색어의 **첫 부분**만 매칭 (중간 매칭 X)
- 자동완성 결과는 **상위 5개**, 질의 빈도 기준 인기순
- 다국어는 설계상 고려만, 실제로는 소문자 영어만 가정

**규모 추정**

- DAU 1,000만 명, 1인당 하루 10건 검색, 검색어당 평균 20바이트(4단어×5글자)
- 타이핑 한 글자마다 요청이 가므로 검색 1건당 실제로는 20건의 백엔드 요청 발생 (예: dinner → d, di, din...)
- **QPS ≈ 24,000**, 최대 QPS ≈ 48,000
- 신규 검색어 비중 20% → 하루 약 0.4GB 신규 데이터 유입

## 2단계: 개략 설계

시스템을 두 서비스로 분리:

- **데이터 수집 서비스**: 사용자 입력 질의를 실시간 수집, `(검색어, 빈도)` 테이블 구성
- **질의 서비스**: `SELECT * FROM frequency_table WHERE query LIKE 'prefix%' ORDER BY frequency DESC LIMIT 5` 같은 쿼리로 응답

→ 문제점: 데이터·요청량이 늘면 DB가 병목됨

## 3단계: 상세 설계 (핵심)

!image.png

**트라이(Trie) 자료구조 채택**

- 루트는 빈 문자열, 각 노드는 문자 하나(최대 26개 자식), 리프까지 가면 하나의 단어 완성
- 각 노드에 빈도 정보까지 저장해야 인기 검색어를 찾을 수 있음
- 순진하게 구현하면 최악의 경우 트라이 전체 탐색 필요 → 성능 최적화 필요:
    - 캐싱전 (순진한 트라이 검색)
        
        !image.png
        
        > 총합: O(p) + O(c) + O(c log c)
        > 
    
    <aside>
    
    ### 해결
    
    1. **접두어 최대 길이 제한** → 노드 탐색 시간 O(p) → O(1)
    2. **각 노드에 인기 검색어 Top5를 캐시** → 조회 시간도 O(1) (단, 저장 공간 트레이드오프)
    </aside>
    

**데이터 수집 서비스 아키텍처**

- Analytics logs(원본 질의 로그) → Aggregators(취합/전처리, DB 저장) → Workers(비동기로 트라이 생성) → Trie Cache(빠른 읽기용, 주기적 DB 스냅샷) → Trie DB(문서 저장소 or 키-값 저장소)
- 타이핑마다 실시간 트라이 갱신은 하지 않음 — 인기 검색어는 자주 바뀌지 않으므로 **주기적 배치 갱신**(예: 주 1회 통째로 새 트라이 생성 후 교체)이 충분

**질의 서비스**

- 요청 → 캐시 조회 → 없으면 DB 조회 후 캐시 채움
- 최적화: AJAX 요청, 브라우저 캐싱, 데이터 샘플링(로그 N건 중 1건만 기록)

**트라이 갱신 방식**

- (a) 전체 재생성 후 교체 (일반적) vs (b) 개별 노드 갱신 — 단, 상위 노드도 하위 인기어를 캐시하고 있어 개별 갱신 시 상위 노드까지 연쇄 갱신해야 하는 번거로움 있음

**검색어 삭제**

- 부적절한 검색어를 걸러내야 할 때는 서버-트라이 캐시 사이에 **필터 계층**을 둬서 처리

**저장소 확장(샤딩)**

- 첫 글자 기준 샤딩 가능하지만 최대 26대로 제한되고 알파벳별 분포가 불균등(c로 시작 단어 ≫ x로 시작 단어)
- 해결책: **샤드 관리자(shard map manager)** 를 둬서 어떤 검색어가 어느 샤드에 있는지 별도 관리

## 4단계: 마무리 (확장 논의)

- **다국어 지원**: 트라이에 유니코드 저장
- **국가별 인기 검색어**: 국가별로 별도 트라이 운용 + CDN으로 응답속도 개선
