# 검색어 자동완성 시스템 설계

검색어 자동완성이란 검색창에 단어를 입력하다 보면 입력 중인 글자에 맞는 검색어가 자동으로 완성되어 표시되는 기능이다. 이번 장에서 가장 많이 이용된 검색어 k개를 자동완성하여 출력하는 시스템을 설계한다.

## 문제 및 설계 범위 확정
- 사용자가 입력하는 단어는 자동완성될 검색어의 첫 부분으로 한정한다.
- 5개의 자동완성 검색어가 표시되어야 한다.
- 질의 빈도에 따라 정해지는 검색어 인기 순위를 기준으로 보여준다.
- 맞춤법 검사나 자동수정은 지원하지 않는다.
- 영어 소문자로 질의가 이루어진다고 가정한다.
- DAU 기준 천만명으로 한다.

### 요구사항
- 빠른 응답 속도 : 사용자가 검색어를 입력함에 따라 자동완성 검색어도 빠르게 표시되어야 한다. 실제로 페이스북 검색어 자동완성 시스템에 대한 문서에서는 시스템 응답속도는 100밀리초 이내여야 한다고 한다.
- 연관성 : 자동완성되어 출력되는 검색어는 사용자가 입력한 단어와 연관되어야 한다.
- 정렬 : 인기도 등 순위 모델에 의해 정렬되어 있어야 한다.
- 규모 확장성 : 많은 트래픽을 감당할 수 있어야 한다.
- 고가용성 : 시스템의 일부에 장애가 발생하거나, 느려지거나 해도 시스템은 계속 사용 가능해야 한다.

## 개략적 설계안
개략적으로 시스템은 크게 두 부분으로 나눌 수 있다.

1. 데이터 수집 서비스(data gathering service) : 사용자가 입력한 질의를 실시간으로 수집하는 시스템이다. 데이터가 많은 애플리케이션에 실시간 시스템은 바람직하지는 않지만, 처음 출발점으로는 좋아 보인다.
2. 질의 서비스 : 주어진 질의에 다섯 개의 인기 검색어를 정렬해 내놓는 서비스다.

### 데이터 수집 서비스
큰 동작은 다음과 같다.
질의문과 사용빈도를 저장하는 빈도 테이블이 있다고 가정한다. 처음에 이 테이블은 비어 있는데,
사용자가 twitch twitter twitter twillo를 순서대로 검색하면 질의 테이블이 다음과 같이 변한다.

| query | frequency |
| :--- | :--- |
| twitch | 1 |

| query | frequency |
| :--- | :--- |
| twitch | 1 |
| twitter | 1 |

| query | frequency |
| :--- | :--- |
| twitch | 1 |
| twitter | 2 |

| query | frequency |
| :--- | :--- |
| twitch | 1 |
| twitter | 2 |
| twillo | 1 |

### 질의 서비스
DB 테이블과 같은 빈도 테이블이 있는 상태라고 하자. 두 개의 필드가 있다.
query : 질의문 저장 필드
frequency : 질의문이 사용된 빈도를 저장하는 필드

이 상태에서 사용자가 어떠한 단어를 검색창에 입력하면 top5 자동완성 검색어가 표시되어야 한다.
top5 검색어는 SQL 질의문을 사용해 계산할 수 있다.

SELECT * FROM frequency_table WHERE query LIKE 'prefix%' ORDER BY frequency DESC LIMIT 5

데이터 양이 적을 때는 나쁘지 않다. 하지만 데이터가 아주 많아지면 데이터베이스에 병목이 올 것이다.

## 상세 설계
데이터 수집 서비스와 질의 서비스 두 부분으로 구성된 개략적 설계안은 최적화된 결과물은 아니지만 출발점으로서는 괜찮은 아이디어였다.
컴포넌트 몇개를 골라 상세히 설계하고 최적화를 진행한다.

### 트라이 자료구조
앞에서 관계형 데이터베이스를 저장소로 사용했다. 하지만, TOP5를 골라내는데 관계형 데이터베이스는 적합하지 않다.
이것을 트라이(접두어 트리)를 사용해 해결한다. 

트라이가 무엇인지 간단하게 살펴본다.
트라이는 retrieval이라는 단어에서 온 것이고, 문자열을 꺼내는 연산에 초점을 맞추어 설계된 자료구조이다.
트리 형태의 자료구조로, 루트 노드가 빈 문자열을 나타내고, 26개의 자식 노드를 가질 수 있다.(알파벳이 26개이기 때문)
각 트리 노드는 하나의 단어, 또는 접두열 문자열을 나타낸다.

기본 트라이 자료구조는 노드에 문자들을 저장하는데, 이용 빈도에 따라 정렬된 결과를 내놓기 위해서는 노드에 빈도 정보까지 저장해야 한다. 

p : 접두어의 길이
n : 트라이 안에 있는 노드 개수
c : 주어진 노드의 자식 노드 개수

가장 많이 사용된 질의어 k개를 찾을 때,
1. 해당 접두어를 표현하는 노드를 찾는다 - 시간복잡도는 O(p)
2. 해당 노드부터 시작되는 하위 트리를 탐색하여 모든 유효 노드를 찾는다. 유효한 검색 문자열을 구성하는 노드가 유효 노드다. - 시간복잡도는 O(c)
3. 유효 노드들을 정렬하여 가장 인기 있는 검색어 k개를 찾는다. 시간복잡도는  O(clogc)

사실 이 알고리즘은 직관적이지만 k개를 얻으려고 전체 트라이를 다 검색해야 한다. 이 문제를 해결하기 위해
1. 접두어의 최대 길이를 제한
2. 각 노드에 인기 검색어를 캐시한다.

### 접두어 최대 길이 제한
사용자가 검색창에 긴 검색어를 입력하는 일은 거의 없다. p값을 작은 정숫값이라고 가정해도 안전하다.
검색어의 최대 길이를 제한할 수 있다면 접두어 노드를 찾는 단계의 시간 복잡도가 O(p)에서 O(1)로 바뀐다.

### 노드에 인기 검색어 캐시
각 노드에 k개의 인기 검색어를 저장해 두면 전체 트라이를 검색하는 일은 방지할 수 있다. -> 사실 각 노드에 질의어를 저장할 공간이 엄청 많이 필요하게 되는데, 빠른 응답속도가 아주 중요할 때는 이 정도 저장공간은 희생되어도 그만한 가치가 있다고 판단된단다.
-> 이 캐시 데이터들을 어떤 주기로 갱신해줘야 할지는 미지수

이렇게 되면 접두어 찾는 시간복잡도와 최고 인기검색어 5개를 찾는 시간복잡도가 O(1)로 바뀐다.

### 데이터 수집 서비스
지금까지 살펴본 설계안은 사용자가 검색창에 타이핑을 할 때마다 실시간으로 데이터를 수정하는데,
1. 매일 수천만 건의 질의가 입력되면 그때마다 트라이를 갱신하면 질의 서비스가 심각하게 느려진다.
2. 트라이가 만들어지고 나면 인기 검색어는 그다지 자주 바뀌지 않으므로 자주 갱신할 필요가 없다.

규모 확장이 쉬운 데이터 수집 서비스를 만들려면 데이터가 어디서 오고 어떻게 이용되는지를 살펴야 한다. 사실 트위터 같은 실시간 애플리케이션은 제안되는 검색어를 신선하게 유지해줘야 하는데, 구글은 그에 비해 자주 바꿔줄 필요가 없다. -> 요구사항에 따라 달라짐

용례가 달라지더라도 데이터 수집 서비스의 토대는 바뀌지 않는다. 보통 이 데이터들은 데이터 분석 서비스나 로깅 서비스에서부터 온다.

### 데이터 분석 서비스 로그
데이터 분석 서비스 로그에는 검색창에 입력된 질의에 관한 원본 데이터가 보관된다. 새로운 데이터가 추가될 뿐 수정은 안 이루어지며, 인덱스도 안건다.

### 로그 취합 서버
데이터 분석 서비스로부터 나오는 로그는 양이 엄청나고 데이터 형식도 제각각이다. 이 서버에서 데이터를 잘 취합해서 시스템이 쉽게 소비하도록 해줘야 한다. 이렇게 취합한 데이터들은 주마다 취합되어 사용된 횟수가 계산되어 저장된다.
이때 작업 서버가 주기적으로 비동기적 작업을 실행해서, 트라이 자료구조와 트라이 데이터베이스에 저장해준다.

### 트라이 데이터베이스
트라이 데이터베이스로 2가지 종류 중 선택할 수 있겠다.
1. 문서 저장소 : 새 트라이를 매주 만들므로, 주기적으로 트라이를 직렬화하여 DB에 저장할 수 있다. 몽고DB같은 문서 저장소를 활용하면 이런 데이터를 편리하게 저장할 수 있다.
2. 키-값 저장소 : 트라이는 아래 로직을 적용해서 해시 테이블 형태로 변환 가능하다.
- 트라이에 보관된 모든 접두어를 해시 테이블 키로 변환
- 각 트라이 노드에 보관된 모든 데이터를 해시 테이블 값으로 변환

이 과정을 거쳐 각 트라이 노드는 하나의 <키,값> 쌍으로 변환된다.

### 질의 서비스 최적화 (Query Service Optimization)
실시간 질의 서비스는 100ms 이내의 응답 속도를 보장해야 하므로 추가적인 최적화 기법이 적용된다.

- **In-Memory 캐싱:** 자주 검색되는 접두어와 추천 결과(Top 5)는 API 서버 앞단의 트라이 캐시에 보관하여 DB 접근을 최소화한다.
- **클라이언트 측 디바운싱 (Debounce):** 사용자가 타이핑하는 매 순간마다 서버로 요청을 보내는 대신, 일정 시간(예: 100ms) 동안 입력이 멈췄을 때만 비동기 요청(AJAX)을 보낸다.
- **브라우저 캐싱 (Browser Caching):** 한 번 수신한 자동완성 추천 결과는 브라우저 캐시에 보관하여 동일한 접두어 입력 시 서버 요청 없이 즉시 반환한다.

### 트라이 샤딩 (Sharding)
트라이 데이터의 크기가 한 대 서버의 메모리 용량을 초과할 경우, 데이터를 여러 서버로 분산해야 한다.

- **알파벳 기준 분산:** 접두어의 첫 글자를 기준으로 샤딩할 수 있으나(예: a~m은 서버 1, n~z는 서버 2), 특정 알파벳(s, t 등)으로 시작하는 단어가 훨씬 많아 데이터 불균형이 발생한다.
- **샤드 관리자 (Shard Manager):** 과거 검색 빈도 데이터를 분석하여 각 샤드에 데이터가 균등하게 배치되도록 동적으로 검색어 공간을 분할 관리한다.

### 필터링 서비스 (Filtering Layer)
자동완성 결과에 비속어, 19금 키워드, 저작권 침해 요소 등 부적절한 단어가 노출되지 않도록, 트라이 노드와 질의 서비스 사이에 블랙리스트 기반의 필터링 레이어를 두어 추천 결과에서 제외한다.
