# 검색어 자동완성 시스템(Search Autocomplete System) 설계

## 검색어 자동완성이란

사용자가 검색창에 글자를 입력하면, 그 접두어로 시작하는 인기 검색어들을 실시간으로 제안해주는 기능이다. 구글 검색창에 "dinner"를 치면 "dinner ideas", "dinner recipes" 같은 추천이 뜨는 게 이것이다. 타입어헤드(typeahead), 자동완성(autocomplete)이라고도 부른다.

## 문제 이해 및 설계 범위 확정

질문을 통해 요구사항을 확정한다.

- **매칭이 검색어의 앞부분에서만 일어나나, 중간에서도 되나?** 앞부분(접두어, prefix)에서만 매칭된다.
- **몇 개의 자동완성을 보여줘야 하나?** 5개
- **어떤 자동완성이 보여야 하나(정렬 기준)?** 인기도(popularity), 즉 검색 빈도가 높은 순.
- **맞춤법 검사 기능이 필요한가?** 지금은 아니다.
- **쿼리는 영어인가?** 영어라고 가정한다(추후 다국어 확장 가능).
- **대문자나 특수문자를 허용하나?** 소문자만 가정한다.
- **얼마나 많은 사용자가 쓰나?** DAU 1,000만 명

### 개략적 규모 추정

```
DAU 1,000만
1인당 하루 평균 10회 검색 가정
한 번 검색에 단어 20자 입력, 글자마다 요청 발생 가정
→ 초당 약 24,000건의 질의(QPS)
→ 최대 QPS는 그 2배로 잡음
→ 질의의 약 20%가 새로운 검색어라고 가정
```

여기서 중요한 관찰: **글자를 하나 칠 때마다 요청이 발생한다.** "dinner"를 치면 d, di, din, dinn, dinne, dinner — 6번의 요청이 나간다. 그래서 자동완성은 **일반 검색보다 훨씬 많은 요청**을 감당해야 하고, 응답이 극도로 빨라야 한다(보통 100ms 이내).

## 자동완성의 두 가지 핵심 요구

이 시스템의 성능은 두 가지에 달려 있다.

1. **빠른 응답 속도**: 사용자가 글자를 칠 때마다 100ms 안에 추천이 떠야 한다. 페이스북 연구에 따르면 자동완성이 100ms보다 느리면 버벅이는 느낌을 준다.
2. **연관성**: 추천 검색어가 입력한 접두어와 관련 있어야 하고, 인기순으로 정렬되어야 한다.

이 두 요구를 동시에 만족시키는 것이 설계의 핵심이고, 그 열쇠가 **트라이(Trie) 자료구조**다.

## 왜 단순한 방법으로는 안 되는가

트라이가 왜 필요한지 이해하려면, 먼저 "그냥 DB로 하면 왜 안 되는지"를 봐야 한다.

검색어와 빈도를 관계형 DB 테이블에 저장했다고 하자.

```
frequency 테이블
| query           | frequency |
| dinner ideas    | 15000     |
| dinner recipes  | 12000     |
| dinner near me  | 8000      |
```

사용자가 "din"을 치면 이런 쿼리를 날려야 한다.

```sql
SELECT * FROM frequency
WHERE query LIKE 'din%'
ORDER BY frequency DESC
LIMIT 5;
```

이게 왜 문제인가:
- **`LIKE 'din%'`가 느리다.** 데이터가 수억 건이면 여전히 느리다.
- **매 글자마다 이 쿼리가 날아간다.** "dinner"면 6번. DAU 1,000만이면 초당 수만 건의 이런 쿼리가 발생한다.
- **정렬 비용**: 매칭된 결과를 빈도순으로 정렬하는 것도 비싸다.

핵심 문제는 **"접두어로 시작하는 것들을 빠르게 찾고, 그중 인기순 top 5를 즉시 반환"** 하는 연산이 관계형 DB에 최적화되어 있지 않다는 것이다. 이걸 잘하는 자료구조가 필요하다. 그게 트라이다.

## 트라이(Trie) 자료구조

### 트라이란

트라이는 **문자열을 저장하고 접두어로 검색하는 데 특화된 트리 자료구조**다. 이름은 re**trie**val(검색)에서 왔고, 접두어 트리(prefix tree)라고도 부른다.

### 기본 구조

핵심 아이디어는 **문자열을 글자 단위로 쪼개서, 공통 접두어를 공유하는 경로로 저장**하는 것이다.

```
"tea", "ted", "ten", "to" 를 저장한 트라이:
            (root)
           /      \
          t        ...
         / \
        e   o        ← "to"
       /|\
      a d n          ← "tea", "ted", "ten"
```

- **루트 노드**는 빈 문자열을 나타낸다.
- 각 노드는 최대 26개(알파벳 소문자)의 자식을 가질 수 있다.
- 루트에서 특정 노드까지 내려가는 **경로**가 하나의 문자열(접두어)이 된다.
- "tea"와 "ted"와 "ten"은 앞의 "te"를 **공유**한다.

### 접두어 검색이 왜 빠른가

"te"로 시작하는 단어를 찾는다고 하자.

```
1. 루트에서 시작
2. 't' 자식으로 이동
3. 'e' 자식으로 이동
4. 이제 이 'e' 노드 아래에 있는 모든 단어가 "te"로 시작하는 단어들이다
```

**접두어를 찾는 데 걸리는 시간은 접두어의 길이에만 비례한다.** "te"는 2글자니까 2번의 이동이면 끝난다. 트라이에 단어가 100만 개든 1억 개든 상관없다.

```
관계형 DB (LIKE 'te%'):
  전체 데이터 양에 비례해서 느려짐

트라이:
  접두어 길이에만 비례 O(접두어 길이)
  → 데이터가 아무리 많아도 "te"는 항상 2번 이동
```

### 자동완성을 위한 확장: 노드에 빈도 저장

기본 트라이는 "이 접두어로 시작하는 단어가 있나?"는 빠르게 답하지만, 자동완성은 **"그중 인기순 top 5"** 가 필요하다. 그래서 트라이를 확장한다.

**각 단어 노드에 빈도(frequency)를 저장한다.**

```
"tea" 노드 → 빈도 14
"ted" 노드 → 빈도 8
"ten" 노드 → 빈도 12
```

**"te"를 치면:**

```
1. "te" 노드까지 이동 (2번)
2. 그 아래 모든 단어를 수집: tea(14), ted(8), ten(12)
3. 빈도순 정렬 후 top 5 반환: tea(14), ten(12), ted(8)
```

### 자동완성 조회 알고리즘과 복잡도

접두어를 `p`, 트라이에 저장된 검색어 수를 `n`, 한 접두어 아래 자식 노드의 수를 `c`라고 하면:

```
1단계: 접두어에 해당하는 노드를 찾는다 → O(p)
2단계: 하위 트리 전체를 탐색해 모든 검색어를 수집 → O(c)
3단계: 빈도순 정렬 후 top k를 뽑는다 → O(c log c)

전체: O(p) + O(c) + O(c log c)
```

문제는 `c`다. 접두어가 짧을수록(예: "a") 그 아래 단어가 폭발적으로 많아져서, 매 요청마다 수십만 개를 모아 정렬하게 된다. 그래서 최적화가 필요하다.

### 기본 방식의 한계와 최적화

**최적화 1: 각 노드에 top-k를 미리 캐싱**

각 노드가 "나(이 접두어) 아래에서 가장 인기 있는 k개 검색어"를 미리 저장해둔다.

```
"te" 노드 → 미리 계산된 top 5: [tea, ten, ted, ...]
"te"를 치면:
  → "te" 노드로 이동 (2번)
  → 거기 저장된 top 5를 그냥 반환 (정렬 불필요!)
  → O(접두어 길이)로 끝
```

조회 시점에 정렬을 아예 안 한다. 미리 만들어둔 답을 꺼내기만 하면 된다.

> 앞서 뉴스 피드에서 "피드를 미리 만들어둔다(Push 모델)"와 같은 발상 — **읽기를 빠르게 하기 위해 쓰기 시점에 미리 계산**하는 것이다.

복잡도로 보면 순진한 방식의 뒤 두 항이 사라지고, 접두어 노드까지 가는 `O(p)`에 저장된 top-k를 꺼내는 `O(1)`만 남는다. 접두어에 길이 상한(예: 최대 50)을 두면 사실상 **`O(1)`에 가까운 조회**가 된다.

다만 각 노드가 top-k를 들고 있어야 하므로 **메모리를 더 쓴다.** 응답 속도와 저장 공간 사이의 트레이드오프다.

**최적화 2: 트라이의 깊이 제한**

접두어 길이에 상한을 둔다(예: 최대 50자). 트라이 깊이가 일정 이하로 유지되어 탐색 시간이 보장된다.

### 트라이 갱신(업데이트)

검색어 빈도는 시간에 따라 계속 바뀐다. 두 가지 방법이 있다.

**방법 1: 트라이를 주기적으로 재구축**

매주 한 번처럼 정해진 주기로 트라이를 통째로 다시 만든다. 검색어 빈도가 실시간으로 정확할 필요가 없다면 이 방법으로 충분하다. 새 트라이를 다 만든 뒤 기존 것과 교체하면 갱신 중에도 서비스가 멈추지 않는다.

**방법 2: 노드를 직접 갱신**

특정 검색어의 빈도가 바뀌면 해당 노드를 직접 고친다. 문제는 top-k 캐시다. 한 단어의 빈도가 바뀌면 루트까지 이어지는 **모든 조상 노드의 top-k 캐시**를 다시 계산해야 할 수 있다.

```
"tea"의 빈도가 확 오름
  → "tea" 노드뿐 아니라
  → "te", "t", 루트의 top 5까지 재검토 필요
```

실무에서는 대개 방법 1(주기적 재구축)을 기본으로 삼고, 실시간성이 중요한 일부만 방법 2로 처리한다.

### 검색어 빈도는 어떻게 계산하나

- **샘플링**: 모든 검색이 아니라 N번에 1번만 로그를 남겨 집계한다. 인기 검색어의 상대 순위를 파악하는 데는 전수 집계가 필요 없다.
- **배치 집계**: 맵리듀스(MapReduce) 같은 분산 처리로 로그를 주기적으로 집계한다.

### 트라이가 선택되는 이유 정리

| 요구사항 | 트라이가 만족시키는 방식 |
|---|---|
| 접두어 매칭 | 트라이의 경로 = 접두어. 애초에 접두어 검색용 자료구조 |
| 빠른 응답 (100ms 이내) | 조회가 접두어 길이에만 비례. 데이터 양과 무관 |
| 인기순 정렬 | 각 노드에 빈도/top-k를 저장해 확장 |
| 대량 데이터 | 공통 접두어를 공유해 메모리 효율적. 데이터 늘어도 조회 속도 유지 |

## 시스템 설계

자동완성 시스템은 크게 두 부분으로 나뉜다.

### 1. 데이터 수집 서비스(Data Gathering Service)

사용자의 검색 질의를 모아서 트라이를 만들고 갱신하는 부분이다.

```
검색 로그 (Analytics Logs)
   ↓
집계 서버 (Aggregators) — 검색어별 빈도 집계
   ↓
집계된 데이터 (Aggregated Data)
   ↓
트라이 구축 작업자 (Trie Builder) — 트라이 생성
   ↓
트라이 DB (Trie Database) — 구축된 트라이 저장
```

> **왜 실시간 갱신을 안 하나?**
> 자동완성 추천은 실시간성이 그렇게까지 중요하지 않다. 어제의 인기 검색어와 지금의 인기 검색어가 크게 다르지 않다. 반면 매 검색마다 트라이를 갱신하면 쓰기 부하가 폭발한다. "약간 오래된 데이터를 감수하고 갱신 비용을 아끼는" 결정 — 앞서 다룬 결과적 일관성과 같은 트레이드오프다.

### 2. 질의 서비스(Query Service)

사용자가 글자를 칠 때 트라이에서 top 5를 찾아 반환하는 부분이다.

```
사용자가 "din" 입력
   ↓
로드밸런서 → API 서버
   ↓
트라이 캐시(Redis 등)에서 "din" 노드의 top 5 조회
   ↓ (캐시 미스면 트라이 DB에서)
top 5 반환
```

**트라이를 캐시에 올린다.** 트라이는 읽기 전용에 가깝고(주기적으로만 갱신) 크기도 관리 가능해서 캐싱에 적합하다.

## 트라이 저장 방법

**방법 1: 문서형 저장소(Document Store)**

트라이를 직렬화(serialize)해서 통째로 저장하고, 주기적으로 다시 만들어 갱신한다.

**방법 2: 키-값 저장소**

트라이를 키-값 형태로 변환한다. 트라이의 모든 접두어를 키로, 그 접두어의 top 5를 값으로 저장한다.

```
"te"  → [tea, ten, ted, ...]
"tea" → [tea, teach, team, ...]
"din" → [dinner, dining, ...]
```

이렇게 하면 조회가 단순 키 조회가 되어 매우 빠르다. 앞서 6장에서 다룬 분산 키-값 저장소가 여기서 활용된다.

## 규모 확장: 트라이 샤딩

트라이가 한 서버 메모리에 안 들어갈 만큼 커지면 여러 서버로 나눠야 한다.

**단순한 방법: 첫 글자로 샤딩**

```
a~i 로 시작하는 검색어 → 서버 1
j~r 로 시작하는 검색어 → 서버 2
s~z 로 시작하는 검색어 → 서버 3
```

문제: 알파벳별로 검색어 양이 균등하지 않다. 's'로 시작하는 단어가 'x'로 시작하는 단어보다 훨씬 많아 부하가 불균등해진다.

**개선: 과거 데이터 기반 샤딩**

검색어 분포 통계를 이용해, 각 샤드가 비슷한 양을 담당하도록 경계를 조정한다. "s"가 너무 많으면 "sa~sm"과 "sn~sz"로 더 쪼갠다. 샤드 매핑을 별도로 관리하는 컴포넌트(shard map manager)를 둔다.

## 마무리: 추가로 논의할 점

- **다국어 지원**: 트라이에 유니코드 데이터를 저장하면 된다.
- **국가별 인기 검색어 차이**: 나라마다 다른 트라이를 만들고, CDN에 트라이를 저장해 응답 속도를 높인다.
- **실시간 검색어 반영**: 방금 화제가 된 검색어(예: 속보)를 반영하려면, 실시간 스트림 처리(예: 아파치 카프카 + 스파크 스트리밍)로 트라이 일부를 빠르게 갱신하는 하이브리드를 고려한다.
- **맞춤법 교정, 개인화** 등도 확장 주제다.

## 정리

검색어 자동완성의 핵심 도전은 **"글자를 칠 때마다, 접두어로 시작하는 인기 검색어 top 5를 100ms 안에"** 라는 요구다. 관계형 DB의 `LIKE` 검색으로는 이 속도와 부하를 감당할 수 없다.

해답은 **트라이**다. 트라이는 접두어를 경로로 저장해서, 데이터가 아무리 많아도 접두어 길이만큼의 시간에 검색이 끝난다. 여기에 각 노드마다 top-k를 미리 캐싱하면, 조회 시점의 정렬조차 없앨 수 있다(쓰기 때 미리 계산 = 뉴스 피드의 Push 모델과 같은 발상).

시스템은 배치로 트라이를 구축하는 **데이터 수집 서비스**와, 트라이를 캐시에서 조회하는 **질의 서비스**로 나뉜다. 트라이가 커지면 첫 글자 기반 샤딩(부하 균등을 위해 분포 기반으로 조정)으로 확장한다. 자동완성은 "미리 계산해서 읽기를 극한으로 빠르게 만드는" 설계 철학이 트라이라는 자료구조로 구현된 사례다.
